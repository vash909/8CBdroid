# Acoustic desktop interoperability

This bench exercises the production **Operate** receiver and manual one-slot
sender using a phone's built-in microphone/speaker and a PC's physical speakers/
microphone. Incoming PCM is generated by the pinned original WSJT-CB routines;
outgoing phone audio is recorded and independently decoded. It does not control
a radio, enable AutoSeq or confirm an RF contact.

This is a manually paced exchange. The host waits for a complete new RX window
after output recovery; it does not qualify reception of a reply in the immediately
following 15-second slot. The receiver currently discards its first partial UTC
window after reopening. That boundary needs separate qualification before
automatic alternating-slot operation can be advertised.

## Scenarios

The [scenario inputs](../reference/wsjtcb/acoustic-cases.json) define 20 audio
events and one explicit receiver restart:

- A trailing hashed sender is unknown in a cold session, resolves after its CQ,
  and becomes unknown again after restarting RX. Both hash orientations are used.
- A complete manually stepped answering exchange with numeric-prefix peer
  `001AB123`: received CQ, sent reply, received report, sent R-report, received
  RR73 and sent 73. The incoming CQ is attenuated by 18 dB digitally.
- A complete manually stepped calling exchange with slash peer `999ZZ/ZZ`:
  sent CQ, received reply, sent report, received R-report, sent RR73 and received 73.
- A slash-call CQ mixed with deterministic Gaussian noise at 0 dB signal/noise
  power over the 12 kHz sample stream, before peak normalization. This is an
  injected digital ratio, not an FT8 2500 Hz SNR measurement or sensitivity limit.
- Finals addressed to other calls never change the selected peer/message,
  arm TX or start output. No received message takes an automatic action.

Expected 77-bit payloads and cold/warm text come from a fresh build of the
checksum-verified pinned desktop packer/unpacker, not the Kotlin implementation.
The generated [test asset](../app/src/androidTest/assets/acoustic.json) records
input/source digests. CI regenerates and compares it:

```bash
python3 scripts/wsjtcb_acoustic.py --check
```

Every output requires explicit Enable TX and Send one slot through the actual
Operate controls. Each completed slot disarms and reopens a fresh receiver with
no old rows or learned hashes. Both even and odd output periods are covered.
Received identities must have the expected peer-selection eligibility; unknown
senders and one-call report/final text cannot invent a sender.

## Physical reproduction

Use the [development compiler setup](DEVELOPMENT.md#desktop-reference-and-native-checks).
The PC also needs NumPy, SciPy, PipeWire utilities, libpulse-simple, an NTP-
synchronized clock and an installed **WSJT-CB** `jt9` decoder. WSJT-X is not a
substitute for its CB message handling. Select a physical PC microphone, not a
speaker monitor or virtual loopback. Position the unlocked phone near the PC
speakers and microphone at audible, unclipped levels.

If NumPy/SciPy are absent, use an isolated host environment:

```bash
python3 -m venv .tooling/audio-host
.tooling/audio-host/bin/python -m pip install numpy scipy
source .tooling/audio-host/bin/activate
```

Missing analysis dependencies fail before any phone operation or audio playback.

Install matching app/test APKs. Save station `1AT106` with a valid locator,
apply a Phone input/output profile, grant microphone permission and open Operate.
Tests do not edit persistent station/profile settings. Keep the app visible and
allow approximately 10–15 minutes; the entire phone scenario is bounded to
1050 seconds and any missing event fails within its own deadline.

```bash
source scripts/env.sh
timeout 1200 python3 scripts/acoustic_checks.py \
  --jt9 /path/to/wsjtcb/jt9 --output /path/to/new-private-directory
```

Use `--ntp-host HOST --ntp-port PORT` for a real NTP endpoint. The suite measures
and applies time within the test process. Each run has unique acknowledgements;
the explicit RX restart renews NTP before the two complete exchanges. If that
measurement reaches five minutes, the test stops RX and renews it before a later
send, with TX idle and disarmed. There is no per-message renewal or relaxed
ten-minute expiry. This test-only policy does not add periodic synchronization
to the client UI.
Received payloads must belong to the precise scheduled UTC slot. Failed audio,
capture or timestamp guards fail the scenario rather than silently retrying or
weakening safety checks. Stop and restart explicitly after correcting setup.

## Independent receive checks

The PC records each outgoing phone slot through its physical microphone, with
capture timestamps. The suite then uses two independent desktop paths:

1. The installed WSJT-CB `jt9` performs its normal FT8 candidate search on the
   recorded UTC window, without a supplied candidate frequency or synthetic
   replacement signal. The decoder receives local/peer call context, but no
   expected payload, tone sequence or forced decoding result.
2. The pinned original LDPC/CRC adapter verifies all 77 payload bits and 79
   observed tones. This second adapter uses known time/frequency and therefore
   does not establish full-desktop search parity. Correlation locates actual
   recorded audio for onset measurements; it never substitutes generated PCM.

The capture must be unclipped. First-tone error must be within 150 ms of UTC
slot +500 ms, with less than 30 ms spread in nearby PC timestamp anchors. These
are bench acceptance bounds, not a universal phone or radio latency guarantee.

Reports retain events, payloads, hash flags, TX periods, source/artifact digests,
desktop text, observed tones and onset/anchor measurements. A failed analysis
can be rerun with `--analyze-only` against the retained `phone-report.json` and
recordings; this performs no playback or phone operation. Recordings may contain
ambient speech and must remain private.

Passing these finite cases supports the tested acoustic integration only. It
does not establish decoder sensitivity, false-positive rates, long-session
reliability, desktop GUI automation, CAT/USB behavior or radio/RF operation.
See [manual operation](MANUAL_OPERATION.md) for operating controls and recovery,
and [validation](VALIDATION.md) for actual tested revisions and results.
